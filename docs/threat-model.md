# 威胁模型与度量边界

## 1. 参与方与信任假设

| 角色 | 拥有的能力 | 信任程度 |
|---|---|---|
| 模型提供方 | 模型权重、加密密钥、KRS 与基线 | 完全可信（信任根） |
| 云运营商 / hypervisor | 主机 root、guest 内存与外设的虚拟化层、磁盘与网络 | **恶意**（本 Demo 的主对手） |
| 云管理员/内部人员 | 同上 + 物理接触（不计物理拆解攻击） | 恶意 |
| AMD | PSP 固件与证书链（ARK/ASK） | 必要信任（硬件信任根，不可去除） |
| 机密 VM 内软件 | 解密后的权重 | 可信（其完整性由度量保证） |

## 2. 覆盖的威胁

**T1 — 权重静态读取**：hypervisor 或管理员直接从磁盘/镜像读取密文
权重。被 AES-256-GCM 加密挡住（密钥只在 KRS，释放前不可解密）。

**T2 — 权重内存读取**：hypervisor 读取运行中 VM 的内存提取明文权重。
被 SEV-SNP 内存加密 + RMP 完整性保护挡住。

**T3 — 运行时篡改后解密**：攻击者篡改内核/initrd/门控程序，让 VM 在
非预期运行时上运行并试图骗取密钥。被度量比对挡住（度量不匹配 →
KRS 拒绝释放）。Demo 的 `tamper-measurement` 场景即此。

**T4 — 报告伪造**：攻击者不入侵 VM，直接伪造一份"好"报告骗密钥。
被 VCEK 签名 + 证书链验证挡住（无私钥不可造合法签名）。`tamper-signature`
场景即此。

**T5 — 报告重放**：重放历史合法报告。被 nonce 挑战 + 一次性 +
TTL + REPORT_DATA 绑定挡住。`tamper-report-data` / `nonce-reuse` 场景。

**T6 — 固件降级攻击**：把平台刷到有已知漏洞的旧固件。被 TCB
分量级防回滚检查挡住。`tamper-tcb` 场景。

**T7 — 密钥释放信道窃听**：KRS↔VM 网络上的窃听者。Demo 用 TLS
（部署要求）；mock 模式仅限 localhost。

## 3. 不覆盖的威胁（明确边界）

**N1 — ROCm 用户态库的运行时完整性**：SEV-SNP 的度量覆盖启动组件
（内核/initrd/早期用户态）。ROCm/vLLM 的用户态 `.so` 在启动度量之外，
本 Demo **不**对它们做完整性校验。缓解路线：IMA appraisal 或
dm-verity 把 ROCm 库纳入度量，再把 IMA 度量聚合进报告（列为
future work，报告中有明确声明）。这是本 Demo 最重要的已知边界。

**N2 — 侧信道**：共享 TLB/缓存/页错误时序、内存带宽侧信道可能
泄露模型结构信息或 prompt 内容。门控不声称解决此问题——这正是
课程论文"隔离 ≠ 负载感知安全"的论点。TEE 内的负载感知防护是
独立的开放问题。

**N3 — 权限提升进 VM 后的软件漏洞**：若 VM 内应用（如 vLLM 服务）
存在 RCE，攻击者可从 VM 内部读明文权重。门控保证"启动时环境可信"，
不保证"运行期代码无漏洞"。

**N4 — AMD/PSP 供应链**：信任根被攻破则一切失效（所有硬件 TEE
方案共同的根本假设）。

**N5 — DoS**：云平台可以直接销毁 VM（拒绝服务），门控不防 DoS，
只保证"不证明就不解密"。

**N6 — KDS 可用性/绑定**：Demo 未校验 VCEK 证书中的 AMD 专有
产品扩展（芯片 SKU 绑定）；生产环境应校验 `amd-sk` 扩展并将允许的
产品型号列入白名单。

## 4. 安全性声明

本项目为课程实践级最小实现，**未经过生产安全审计**，密钥管理
（密钥轮换、HSM 托管、审计日志持久化）、KRS 高可用、证书扩展校验、
IMA 集成均未实现。复现者不应将其用于任何生产场景。
